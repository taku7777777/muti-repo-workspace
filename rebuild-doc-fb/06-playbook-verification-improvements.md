# 06 — プレイブック・検証の改善候補(Medium)

10-rebuild-playbook.md と 08-verification.md への改善提案。方法論(フェーズゲート、
実装/検証の分離、独立レビュー必須)自体は妥当で、実績の裏付けもある。以下は運転を
確実にするための追補。

## 1. 「人間が物理的に必要なゲート」を明示する

再構築エージェントが自力で通過**できない**ゲートが混ざっているが、パックは
区別していない:

- trust ダイアログ承認(08 Step 1 / Step 3 前提 — GUI 操作)
- cmux の実タブ検証(Step 3 — macOS GUI)
- broker の SHA 打鍵(Step 4、R4 ゲート — 設計上 LLM 代打不可が正しい)
- 短命 PAT の発行・export(10 §10.3-4)

**改善候補**: 10 §10.2 の各ゲート表に「自動 / 人間必須」列を追加し、
§10.5 の運転者チェックポイントに「人間必須ゲートの実施はエージェントの報告を
待たず運転者がスケジュールする」を加える。エージェントには「人間必須ゲートに
到達したら停止して運転者を呼ぶ」を絶対条件として雛形プロンプトに足す。

## 2. 要求 → 仕様 → 検証のトレーサビリティ表が無い

FR/NFR/SEC(02)と実装仕様(04/05/06)と検証(08)の対応は概ね取れているが、
表として存在しないため、抜けの検出が読者の注意力頼みになっている。実際に抜けがある:

| 要求 | 検証の現状 |
|---|---|
| FR-2.2 `github-issues` アダプタ | 08 に検証項目なし(Step 2 は手動チケットのみ) |
| FR-2.3 purpose の `mcp_servers` 切替 | 検証項目なし(`.mcp.json` 生成の確認が無い) |
| FR-4.6 `WORKERD_SOCKET` 未設定の単一プロセスフォールバック | 08 §8.2 は分割トポロジのみ検証 |
| FR-4.7 `npm run orchestrate` / `drive` の resume | R5 ゲートにあるが 08 本文に手順なし |
| FR-6.3 複数ワークスペース並走 | 検証項目なし(→ fb 04 参照) |
| NFR-8 可搬性(ワークスペース移動後も worktree リンク維持) | 検証項目なし(相対ターゲットの根拠になっている不変条件なのに) |

**改善候補**: 02 の各要求 ID に「仕様: 04 §x / 検証: 08 Step y」の参照列を付ける
(推奨・機械的な作業)。最低でも上表の6件は 08 に検証手順を追加する。

## 3. R9(ドキュメント)の完了ゲートが検証不能

「設計と実態の乖離ゼロを確認して完了」(10 §10.2 R9)は判定手順が無い。
09 §9.3 が示すとおり、元プロジェクト自身がドキュメント乖離を残した実績がある
(mrw-cli.md の「not built」見出し等)ので、ここは具体化する価値が高い。

**改善候補**: R9 ゲートを「独立コンテキストのレビューエージェントが docs のみを読み、
08 の検証シーケンスを docs の記述どおりに再実行できるか(コマンド・パス・フラグの
逐語一致)を確認する」に置き換える。乖離ゼロの操作的定義になる。

## 4. 雛形プロンプトへの追補

10 §10.4 の雛形は良いが、以下が欠けている:

- **停止条件**: 「仕様間の矛盾を発見した場合は、自己判断で一方を選ばず停止して
  運転者に裁定を求める」(fb 01 の矛盾が現存するため必須)
- **検証リソースの所在**: スクラッチリポジトリ名・PAT の受け渡し方法・使い捨て
  チケットIDの採番規則(TEST-*/DEMO-* とだけあるが、どの org かは運転者が渡す必要)
- **報告書式**: 「ゲート結果は生の出力を添えて」とあるが、置き場所(ブランチ内
  `docs/rebuild-log/` 等)を決めておくと 10.3-5 の「隠さず報告」が監査可能になる

## 5. フェーズ順序の再考(モードB)

- R3 の中間トポロジ問題(fb 05 §3)と併せて、モードB では
  「R3+R6 統合(最初から分割)」を許可する方が、捨てるコードと未仕様領域が減る。
- R1〜R2(ネイティブ経路)は Phase 5 で廃止予定のレイヤに最初の2フェーズを
  投じる構成でもある。日常運用がネイティブ経路である以上スコープに含めるのは
  妥当だが、**コンテナ経路を先に立てる順序(R3〜R7 → R1〜R2 → R8)も許容**すると
  明記しておくと、目的(コンテナ経路のライブ実証 → Phase 5)に対して合理的な
  順序をエージェント/運転者が選べる。worktree/handoff の資産は R1 由来なので、
  その場合は common.sh/worktree 規則(04 §4.7)だけ先行実装する注記が要る。
