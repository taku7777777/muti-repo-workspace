# 07 — 小さな不整合・表記(Low)

単体では実害が小さいが、「文言に忠実な独立エージェント」が消費する文書なので
安価に潰しておく価値があるもの。

## 1. 内部 ID の凡例が無い(F9 は未定義のまま登場)

- `F1〜F6` は broker の6要求として 05/07 で定義されているが、
  **`F9`**(07 INV-7 / 09 §9.5 の excludedCommands 穴)は定義なしで登場する。
  F7/F8 が存在しない連番は「参照先の欠落」に見え、再構築エージェントが
  存在しない凡例を探すコストになる。
- 同様に `C-2` `C-3` `S2-o` `S8-d` `P4-c` は元リポジトリのレビュー/検証記録の
  ID と思われ、初出時に inline 説明はあるものの体系の説明が無い。
- **改善候補**: README に1行凡例を足す(「F- = broker/publish 要求、C- = 既知制約、
  S-/P- = 元リポジトリの検証・レビュー記録の項番(本パックでは出典表示のみの
  意味を持つ)」)。F9 は「F1〜F6 とは別系列のレビュー指摘番号」と明記するか、
  番号を捨てて名前(excludedCommands 連結穴)で呼ぶ。

## 2. テスト数の記法が曖昧で NFR と照合できない

- `02` NFR-6 / `05` §5.7 / `08` §8.2-5 は「harness 81」と言うが、§5.7 の表は
  `workerd-protocol.test.ts(~10×4 ops)` という曖昧な記法を含み、
  合計が 79〜109 のどこにでも読める。再構築の受け入れ基準(≒81)と照合不能。
- **改善候補**: §5.7 の各行を確定数にする(「~」をやめる)か、NFR-6 側を
  「スイート構成が §5.7 と一致し全 green(数は参考値)」に緩める。後者が現実的。

## 3. typo・表記

- `02` FR-7 見出し「コンテナ経路の **публish** 前提」— Cyrillic 文字混入
  (publish)。grep での検索性を壊すので修正。
- `README`/`01` の対象システム名が「muti-repo-workspace」(mutiのまま)。
  リポジトリ名としては実態どおりだが、初見のエージェントが typo と「修正」して
  multi- に直すリスクがある。README に「muti は意図的(既存リポジトリ名)」と
  1行注記すると安全。
- `03` §3.2 の特権マトリクスで Root の「パッケージ導入 / docker」が「プロンプト」
  とあるが、これは permissions の ask を指すと推測される。用語を「ask(確認付き)」に
  統一すると 04 §4.3 との対応が取れる。

## 4. 読み順の記述が README と 01 で二重管理

- README「01 → 02 → 03 → 07 を先に」/ 01 §1.6「02 → 03 → 07 → …」。
  内容はほぼ同じだが二重管理で、改訂時にずれる(すでに 01 を含む/含まないの差がある)。
- **改善候補**: 読み順の正典を README に一本化し、01 §1.6 は README への参照にする。

## 5. 検証記録の残余参照

- `08` §8.1 Step 5 の「Exit 126」等、**観測値ベース**の期待挙動は環境
  (シェル・Claude Code バージョン)で変わりうる。再構築の受け入れ基準としては
  「非ゼロ exit で拒否され、サンドボックス外実行されない」のような
  挙動レベルの記述に落とす方が頑健。
- `08` §8.4 のライブ検証記録は「元システムで何が証明済みか」の記録であって
  再構築側の義務ではないことが、表の位置から読み取りにくい。§8.4 冒頭の1文を
  表の**前**ではなく見出し直下に太字で置く程度でよい。
