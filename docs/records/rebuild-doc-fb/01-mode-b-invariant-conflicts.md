# 01 — モードB と不変条件の正面衝突(Blocker: 文書修正が必要)

## 対象箇所

- `07-security-invariants.md` INV-6 第3項:
  「config 発見の walk-up は3実装(common.sh / pre-push / mrw.mjs)で一致し、
  `tasks/` セグメント配下の `.mrw/` を拒否する」
- `04-native-path.md` §4.10 不変条件 1:
  「config 発見の walk-up は common.sh / pre-push / mrw.mjs で同一の config_dir を解決し…」
- `09-known-issues.md` A 系統 是正方向:
  「**pre-push は walk-up をやめ**、セットアップ時に config パスを焼き込む方式へ」
- `10-rebuild-playbook.md` §10.4 プロンプト雛形:
  「INV-1〜14 は **1つも緩めない**」+「A/B/C 3系統は設計段階から回避」

## 指摘 1: モードB のエージェントは矛盾した命令を受ける

INV-6 と §4.10-1 は「walk-up が3実装で一致する」という**機構**を不可侵条件として
明文化している。一方、モードB で必須の A 系統是正は「pre-push から walk-up を除去」
すること。プロンプト雛形の絶対条件は両方を同時に要求しており、**文言に忠実な
エージェントはここでデッドロックする**(または恣意的にどちらかを破る — どちらに
倒れるか制御できないのが最悪)。

### 根本原因

07 の一部の不変条件が「守るべき成果(outcome)」ではなく「現行実装の機構(mechanism)」
の水準で書かれている。INV-6 が本当に守りたいのは:

> worker がコミット・環境変数・パス汚染のいずれによっても、push ガードが参照する
> allowlist ポリシーを差し替え/偽装/無効化できないこと。

walk-up 一致はその一実装(しかも 09-A が「外部化と両立しない」と判定済みの実装)にすぎない。

### 改善候補(推奨)

1. **INV-6 第3項を成果レベルに書き換える**。例:
   「push ガード(broker in-process / pre-push)が参照するポリシーの解決は、
   worker が書込可能ないかなるパス(`tasks/` 配下・worktree 内コミット含む)からも
   影響を受けてはならない。3実装が同一ポリシーを解決することを検証で保証する
   (機構は walk-up でも焼き込みでもよい)」
2. §4.10-1 に「モードB では 09-A の是正方式(焼き込み)を採ること。その場合も
   本項の成果は維持」と注記する。
3. 07 全体を「outcome / mechanism」で一度監査する。同種の混入は少なくとも
   INV-7 の `.worker-target` 記述(UUID ピンは機構)にもあるが、こちらは
   代替案が提示されていないため実害は薄い。優先は INV-6。

## 指摘 2: モードA(忠実再現)は「INV を1つも手放さない」と両立しない

`01-goals-and-scope.md` §1.4 は「**どちらのモードでも**不可侵不変条件は1つも
手放してはならない」とする。しかし 09-A の欠陥を忠実再現すると:

- 外部 state_root では pre-push が正規 `.mrw/` に到達できず、toolHome の別ポリシー
  (空なら warn-and-allow)へフォールバックする(09-A-2)。
- **ネイティブ経路には broker が存在しない**ため、pre-push は defence-in-depth では
  なく事実上の主防御。それが静かに無効化される状態は INV-6 の成果を満たさない。

つまりモードA は「外部化構成では INV-6 が破れている状態」を再現することになり、
§1.4 の但し書きと矛盾する。

### 改善候補

- **案1(推奨)**: モードA の適用範囲を「legacy 構成(state_root 空・`.mrw/` 不在)に
  限定して忠実再現」と明記する。外部化構成の忠実再現は「既知欠陥の再現を含む」ことを
  成果物ドキュメントに明記させる(09 冒頭の記述を 01 §1.4 にも引き上げる)。
- **案2**: モードA を削除し、モードB 一本にする(モードA の用途 — フォレンジック比較
  など — が実在しないなら、選択肢を残す価値は薄い)。用途があるなら 01 §1.4 に明記する。

## 指摘 3: pre-push の fail-open 範囲が文書間で不一致

- `04-native-path.md` §4.5-2 / `02-requirements.md` NFR-5:
  fail-open(警告 + exit 0)は「**config が読めない / jq 不在**のときのみ」。
- `09-known-issues.md` A-3: 「workspace.json 破損 → …(mrw.mjs は throw、
  **pre-push は fail-closed** — 3実装で失敗セマンティクスが不一致)」。

「読めない(missing/unreadable)」と「破損(パース不能)」で挙動が分かれるのか、
09 の記述が正でどちらかの文書が誤りなのか、判別できない。再構築エージェントは
pre-push の失敗セマンティクスを実装しなければならないため、ここは曖昧のままに
できない。

### 改善候補

失敗クラスごとの規定表を 04 §4.5 に追加する(推奨)。例:

| 失敗クラス | pre-push | common.sh | mrw.mjs |
|---|---|---|---|
| config ファイル不在 | fail-open + 警告 | 既定へフォールバック | 既定へフォールバック |
| jq / パーサ不在 | fail-open + 警告 | die | die |
| config パース不能(破損) | **fail-closed** | die | throw |
| state_root が相対パス | fail-closed | die | throw |

(値は例。モードB では 09-A の「単一 canonicalize+validate」導入と同時に3実装の
セマンティクスを統一し、この表を正典にする。)
